# DESIGN.md — Approach B: Encrypted Envelope over Plain TCP

## 1. Architecture Overview

```
SENDER                                          RECEIVER
──────                                          ────────

  [File on disk]                              [.tmp file on disk]
       │                                              │
       │ read 1 MiB at a time                         │ write plaintext
       ▼                                              ▼
  ┌─────────────┐    Plain TCP socket        ┌──────────────────┐
  │  AES-256-GCM│ ── [len][nonce+ct+tag] ──▶ │  AES-256-GCM     │
  │  encrypt    │                            │  decrypt         │
  │  (per chunk)│                            │  (per chunk)     │
  └─────────────┘                            └──────────────────┘
       │                                              │
       │ [len][JSON manifest + HMAC-SHA256]           │ verify HMAC
       │                                              │ verify SHA-256
       │                                              │ atomic rename
       │                                              │
  [envelope.key]     pre-shared out-of-band     [envelope.key]
  (32 random bytes)  (both sides read key file) (same 32 bytes)


Wire sequence
─────────────
  1. Header frame     JSON: {filename, file_size, total_chunks}
  2. Chunk frames ×N  [nonce (12 B)] [ciphertext + GCM tag (N+16 B)]
                      repeated for each 1 MiB block
  3. Manifest frame   JSON: {manifest: {...}, hmac: "<hex>"}
     manifest fields: version, filename, file_sha256,
                      total_chunks, timestamp (Unix epoch)
```

**Architectural category:** Application-layer envelope encryption with a pre-distributed long-lived symmetric key (PSK). No TLS, no online key exchange — the key is distributed out-of-band before the transfer begins. The wire carries only ciphertext; no key material is ever transmitted.

## 2. Key Exchange and Key Management

| Item | Detail |
|------|--------|
| **Key type** | 32-byte (256-bit) pre-shared symmetric key (PSK), generated by `generate_key.py` using `os.urandom(32)` — a CSPRNG. |
| **Key distribution** | Out-of-band only. Both sender and receiver read the key from a file path passed via `--key-file` or the `ENVELOPE_KEY_FILE` environment variable. The key bytes are never logged, printed, or transmitted on the wire. |
| **Key file permissions** | `generate_key.py` sets mode `0o600` (owner read/write only) on the key file immediately after writing it. |
| **Key usage** | The same 32-byte key serves two purposes: (a) AES-256 key for AESGCM chunk encryption; (b) HMAC-SHA256 key for the signed manifest. Using one key for both is acceptable here because HMAC and AES-GCM are domain-separated by construction — HMAC operates on JSON bytes, AES-GCM operates on plaintext data with a random nonce. |
| **No forward secrecy** | Unlike Approach A (which uses ECDHE inside TLS 1.3), Approach B uses a static PSK. If the key file is later compromised, all past transfers encrypted with it are retroactively exposed — provided the attacker recorded the ciphertext. This is an explicit trade-off for the pre-distributed key model. It is documented here as required by the assessment. |
| **Nonce generation** | `os.urandom(12)` per chunk — 12 cryptographically random bytes. The nonce is prepended to the ciphertext on the wire so the receiver can extract it. Random nonces have a negligible collision probability: for a 4 GiB file at 1 MiB/chunk there are 4,096 nonces; the birthday bound for 96-bit nonces is ~2^48 encryptions. |

## 3. Chunking and Framing

```
┌─────────────────────────────────────────────────────────────────┐
│  All frames share the same length-prefix framing:               │
│                                                                 │
│  ┌──────────┬─────────────────────────────────────────────┐    │
│  │ 4 bytes  │  N bytes  (payload)                         │    │
│  │ BE uint32│                                             │    │
│  └──────────┴─────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘

Frame 1 — Header (JSON)
───────────────────────
  {"filename": "...", "file_size": N, "total_chunks": K}

Frames 2…K+1 — Encrypted chunks
─────────────────────────────────
  ┌────────────┬───────────────────────────────────┐
  │ 12 bytes   │  M bytes                          │
  │ random     │  AES-256-GCM ciphertext + 16-byte │
  │ nonce      │  authentication tag               │
  └────────────┴───────────────────────────────────┘

  AEAD inputs:
    key   = PSK (32 bytes, pre-shared)
    nonce = os.urandom(12) — fresh per chunk, prepended to frame
    aad   = seq_number as 64-bit big-endian (8 bytes)
    plain = up to 1,048,576 bytes (1 MiB)

Frame K+2 — Signed manifest (JSON)
────────────────────────────────────
  {
    "manifest": {
      "version":      1,
      "filename":     "...",
      "file_sha256":  "<hex>",   ← SHA-256 of full plaintext
      "total_chunks": K,
      "timestamp":    <unix epoch seconds>
    },
    "hmac": "<hex>"              ← HMAC-SHA256 over canonical JSON
  }
```

**Chunk size:** 1 MiB (1,048,576 bytes) — constant `CHUNK_SIZE = 1 * 1024 * 1024`.

**Receiver write discipline:** All plaintext is written to `<filename>.tmp`. The manifest HMAC is verified first, then `total_chunks` consistency, then SHA-256 of all received plaintext. Only after all three checks pass does the receiver call `os.rename(tmp_path, final_path)`. If any check fails, the `.tmp` file is deleted and the process exits non-zero.

## 4. Exact Algorithms and Parameters

| Parameter | Value | Justification |
|-----------|-------|---------------|
| **Transport** | Plain TCP (no TLS) | Security is provided entirely at the application layer by AEAD. TLS is not used — this is the key architectural difference from Approach A. |
| **Chunk cipher** | AES-256-GCM | AEAD — provides confidentiality, integrity, and authenticity per chunk in one primitive. NIST SP 800-38D. |
| **Key length** | 256 bits (32 bytes) | AES-256 provides 128-bit security margin. Also the natural key size for HMAC-SHA256. |
| **GCM nonce** | 96 bits (12 bytes), random via `os.urandom` | NIST SP 800-38D §8.2. Random nonces are safe up to ~2^48 encryptions under the same key; well within the 4,096-chunk budget. |
| **GCM tag** | 128 bits (16 bytes) — never truncated | Full-length tag preserves the 2^−128 forgery bound. |
| **AAD** | `seq_number` as 64-bit big-endian (8 bytes) | Binds each ciphertext frame to its position in the sequence. A reordering or splicing attack causes `InvalidTag` on decryption. |
| **Manifest signing** | HMAC-SHA256, keyed with the 32-byte PSK, over `json.dumps(manifest, sort_keys=True).encode("utf-8")` | Deterministic canonical serialisation (sorted keys) prevents ambiguity. `hmac.compare_digest` used for timing-safe comparison. |
| **End-to-end hash** | SHA-256 of concatenated plaintext, carried inside the signed manifest | Detects truncation (missing chunks) and any bit-flip that slipped through GCM (practically impossible, but defence-in-depth). |
| **Timestamp in manifest** | Unix epoch integer, signed by HMAC | Limits replay window — receiver should check that timestamp is within an acceptable freshness window (e.g., ±5 minutes) of its local clock. See §5 replay threat. |
| **Crypto library** | `cryptography` (PyCA) — `AESGCM` + `hmac` (stdlib) | `cryptography` is well-audited. `hmac` is Python stdlib — no external dependency for the MAC layer. |

## 5. Threat Model — Row-by-Row Response

| Threat | CIAA Bucket | Mechanism in This Design | Evidence in Code |
|--------|-------------|--------------------------|-----------------|
| **Passive eavesdropper records the entire TCP stream** | Confidentiality | The transport is plain TCP, but every plaintext byte is encrypted with AES-256-GCM before being placed on the wire. Each chunk frame contains `[12-byte random nonce][ciphertext][16-byte GCM tag]`. An eavesdropper sees only random-looking ciphertext; without the 32-byte PSK they cannot decrypt any chunk. The PSK is never transmitted — it is loaded from a local key file on each side. The header frame (filename, size, chunk count) is sent in plaintext JSON, but contains no file content. | `encrypt_chunk()` in sender.py: `nonce = os.urandom(NONCE_SIZE); ciphertext = aesgcm.encrypt(nonce, plaintext, seq_aad(seq)); return nonce + ciphertext`. The key is loaded from a file: `load_key(args.key_file)`. |
| **Active MITM modifies bytes mid-flight** | Integrity | Each chunk is protected by a 128-bit GCM authentication tag. Any modification to the nonce, ciphertext, or tag causes `AESGCM.decrypt()` to raise `InvalidTag`. The receiver calls `cleanup_and_fail()` immediately, deleting the `.tmp` file. Additionally, the final manifest carries a SHA-256 hash of the entire plaintext, signed with HMAC-SHA256. A MITM that modifies chunks cannot forge a valid HMAC without the PSK. Even if somehow all per-chunk tags were bypassed, the final SHA-256 mismatch would abort the transfer. | `except InvalidTag: cleanup_and_fail(tmp_path, …)` in receiver.py lines 147-152; `if not verify_manifest_hmac(key, manifest, mac_hex): cleanup_and_fail(…)` lines 164-165; `if not hmac.compare_digest(actual_sha256, expected_sha256): cleanup_and_fail(…)` lines 186-192. |
| **Attacker spoofs the sender or receiver** | Authenticity | Authentication is provided by the pre-shared key. Any party that can successfully encrypt chunks with valid AES-GCM tags and produce a valid HMAC-SHA256 manifest must possess the 32-byte PSK. An attacker without the PSK cannot produce a valid GCM tag (forgery probability 2^−128 per attempt) or a valid HMAC (same bound). This is symmetric authentication — it proves possession of the key, not identity by name. Both sides implicitly trust whoever holds the same key file. This is the intended model for pre-distributed keys. | `sign_manifest()` uses `hmac.new(key, payload, "sha256")`; `verify_manifest_hmac()` uses `hmac.compare_digest(expected, received)` for timing-safe comparison. AESGCM tag provides per-chunk sender authentication. |
| **Replay of an earlier valid transfer** | Integrity / Authenticity | The signed manifest includes a `timestamp` field (Unix epoch seconds). Because the manifest is HMAC-signed, an attacker cannot alter the timestamp without invalidating the HMAC. A receiver that checks timestamp freshness (e.g., rejects manifests older than 5 minutes) will reject a replayed transfer. At the per-chunk level, the random nonces mean that even if the same plaintext file is sent twice, each session produces entirely different ciphertext — a captured session cannot be replayed at the chunk level because the nonces differ and the receiver's AEAD state is independent. **Note:** The current receiver implementation verifies the HMAC on the timestamp but does not enforce a freshness window. Adding `if abs(time.time() - manifest["timestamp"]) > 300: cleanup_and_fail(…)` is the recommended hardening step. | `build_manifest()` in sender.py includes `"timestamp": int(time.time())`; `sign_manifest()` covers it; random nonces via `os.urandom(NONCE_SIZE)` per chunk make session ciphertext unique. |
| **Connection drops at 80% transferred** | Availability | All received plaintext is written to `<filename>.tmp` — not the final filename. If the TCP connection drops mid-transfer (raising `ConnectionError` or any other exception), the `cleanup_and_fail()` path deletes the `.tmp` file and exits non-zero. The final `os.rename(tmp_path, final_path)` executes only after the manifest HMAC, chunk count, and SHA-256 all pass. A partial file is never silently left under the final name. The sender can be re-run to restart the transfer from chunk 0. | `tmp_path = final_path + TMP_SUFFIX` in receiver.py line 137; `os.rename(tmp_path, final_path)` line 195 (only reached after all checks); `cleanup_and_fail(tmp_path, …)` on all error paths including `ConnectionError`. |
| **Untrusted intermediary (broker / object store)** | Confidentiality / Integrity | If the TCP connection were routed through a broker or object store (e.g., the ciphertext chunks were buffered by a relay), the broker would see only AES-256-GCM ciphertext. Without the PSK the broker cannot decrypt any chunk (confidentiality). The broker cannot forge a valid GCM tag on modified ciphertext (integrity). Even if the broker reorders, drops, or duplicates chunk frames, the sequence-number AAD causes `InvalidTag` on any reordered chunk, and the chunk-count check in the manifest catches a dropped or duplicated chunk. Plaintext and the PSK never leave the sender or receiver — the broker's compromise does not expose the file contents. | Nonce is in the wire frame (`nonce + ciphertext`), so the broker sees it — but without the PSK, the nonce provides no advantage. AAD = `seq_aad(seq)` ensures broker-induced reordering fails at decryption. HMAC on manifest ensures the broker cannot alter the file hash or chunk count. |

## 6. Known Limitations and Trade-offs

- **No forward secrecy.** A PSK-based design means compromise of the key file retroactively exposes all past transfers whose ciphertext was recorded. Approach A (TLS 1.3 with ECDHE) provides forward secrecy; Approach B intentionally does not, as an explicit architectural contrast.
- **Symmetric identity.** PSK authentication proves key possession, not named identity. If the key file leaks to a third party, that third party can impersonate either side. Key file access control (`0o600` permissions) is the primary defence.
- **Timestamp freshness not yet enforced in receiver.** The manifest timestamp is signed but the receiver does not currently reject stale manifests. Hardening: add `if abs(time.time() - manifest["timestamp"]) > MAX_REPLAY_WINDOW: cleanup_and_fail(…)` with `MAX_REPLAY_WINDOW = 300` seconds.
- **Header is unauthenticated.** The initial JSON header (filename, file size, total chunks) travels before any AEAD. A MITM could alter the declared filename or chunk count. The manifest (which is authenticated) carries the authoritative chunk count, and the receiver cross-checks them — so the only risk from a tampered header is a misleading filename or a denial-of-service (wrong chunk count causes early loop termination, which is caught as a protocol error). Mitigating this fully would require including the header in the manifest AAD.
- **No true resumability.** Same limitation as Approach A — a dropped connection requires a full restart from chunk 0.
